# Resolución Práctica 1: Metodologías de Desarrollo en Cascada

A continuación se presenta el desarrollo completo de los 15 ejercicios planteados, estructurados bajo las fases clásicas del modelo en cascada, aplicados a un sistema de gestión de inventario.

---

## 1. Análisis de Requerimientos

### Ejercicio 1: Requisitos funcionales y no funcionales

Para la aplicación web de gestión de inventario del cliente, se definen los siguientes requerimientos:

**Requisitos Funcionales (Lo que el sistema debe hacer):**

1. **Autenticación:** El sistema debe permitir el inicio de sesión a usuarios administradores mediante correo y contraseña.
2. **Gestión de Catálogo (CRUD):** El sistema debe permitir agregar, visualizar, modificar y dar de baja productos.
3. **Búsqueda y Filtros:** El usuario debe poder buscar productos por nombre, SKU (código de artículo) o categoría.
4. **Control de Stock:** El sistema debe descontar o sumar unidades del inventario al registrar movimientos.
5. **Alertas:** El sistema debe notificar en la interfaz cuando el stock de un artículo sea menor a 5 unidades.

**Requisitos No Funcionales (Cómo debe comportarse el sistema):**

1. **Rendimiento:** Las búsquedas de productos deben resolverse en menos de 1 segundo.
2. **Seguridad:** Las contraseñas deben estar hasheadas (ej. usando bcrypt) en la base de datos.
3. **Disponibilidad:** El sistema debe estar disponible en un entorno web 24/7.
4. **Usabilidad:** Interfaz intuitiva y de diseño _responsive_ (adaptable a PC y móviles).

### Ejercicio 2: Caso de Uso "Agregar un nuevo producto"

- **Nombre del Caso de Uso:** Agregar un nuevo producto al inventario.
- **Actor:** Usuario Administrador.
- **Precondiciones:** El usuario está logueado y se encuentra en la pantalla principal del inventario.
- **Secuencia de Eventos (Flujo Normal):**
  1. El actor hace clic en el botón "Nuevo Producto".
  2. El sistema muestra un formulario en blanco.
  3. El actor ingresa los datos: `Nombre`, `SKU`, `Descripción`, `Precio Unitario`, `Stock Inicial` y `Categoría`.
  4. El actor hace clic en "Guardar".
  5. El sistema valida que el SKU no esté duplicado y que los campos numéricos sean válidos (mayores a cero).
  6. El sistema registra el producto en la base de datos.
  7. El sistema redirige a la lista de inventario y muestra un mensaje: "Producto creado con éxito".
- **Flujo Alternativo (Error de Validación):**
  - Si en el paso 5 el SKU ya existe, el sistema detiene el proceso y muestra el mensaje: "Error: El código SKU ya está registrado".

## 3. Diseño del Programa

### Ejercicio 5: Elección de Arquitectura

Se propone utilizar una **Arquitectura en Tres Capas (Cliente-Servidor)** basada en una API REST.

- **Justificación:** Separar el Frontend (interfaz de usuario), el Backend (lógica de negocio) y la Base de Datos garantiza un alto grado de flexibilidad. Si el cliente el día de mañana quiere una App Móvil, solo se desarrolla un nuevo Frontend, reutilizando todo el Backend intacto. Además, permite a distintos desarrolladores trabajar en paralelo sin pisarse el código.

### Ejercicio 6: Diseño de la Base de Datos (Modelo Relacional)

Se proponen 3 tablas principales:

1. **Tabla `usuarios`:**
   - `id_usuario` (PK, INT, AutoIncremental)
   - `email` (VARCHAR, Unique)
   - `password_hash` (VARCHAR)
2. **Tabla `categorias`:**
   - `id_categoria` (PK, INT)
   - `nombre` (VARCHAR)
3. **Tabla `productos`:**
   - `id_producto` (PK, INT)
   - `sku` (VARCHAR, Unique)
   - `nombre` (VARCHAR)
   - `precio` (DECIMAL)
   - `stock` (INT)
   - `id_categoria` (FK -> categorias.id_categoria)

## 4. Diseño Lógico e Implementación

### Ejercicios 7 y 8: Implementación y Lógica de Negocio (Agregar Producto)

_Basado en los diagramas de clases y robustez, a continuación se presenta un snippet en Python (utilizando FastAPI) que resuelve la lógica de negocio y la creación del producto._

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

# Simulación de la Base de Datos en memoria para el ejercicio
base_de_datos_productos = []

# Definición de la Clase/Entidad Producto (Validación de datos)
class ProductoBase(BaseModel):
    sku: str
    nombre: str
    precio: float
    stock: int
    id_categoria: int

@app.post("/api/productos/")
async def agregar_producto(producto: ProductoBase):
    # 1. Lógica de Negocio: Validar valores negativos (Diagrama de Robustez)
    if producto.precio < 0 or producto.stock < 0:
        raise HTTPException(status_code=400, detail="El precio y stock deben ser positivos.")

    # 2. Lógica de Negocio: Evitar SKU duplicado
    for p in base_de_datos_productos:
        if p.sku == producto.sku:
            raise HTTPException(status_code=409, detail="El SKU ya existe en el sistema.")

    # 3. Implementación: Guardar en la base de datos
    nuevo_producto = producto.dict()
    nuevo_producto["id_producto"] = len(base_de_datos_productos) + 1
    base_de_datos_productos.append(nuevo_producto)

    return {"mensaje": "Producto creado con éxito", "producto": nuevo_producto}
```
